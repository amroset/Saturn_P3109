# gfloat reference model for FP8 conversion tests

The FP8 conversion tests (`vec-mx-unary`) previously took their expected values
from **Spike**, via `gen_data.c` + `gen_data.sh`. Spike implements the OCP FP8
formats but has no IEEE P3109 support, so it cannot remain the golden model once
`FPConv` is retargeted.

The replacement is [gfloat](https://github.com/graphcore-research/gfloat), the
Graphcore-maintained implementation of the P3109 formats, which also covers OCP
FP8 and IEEE 754 through one API.

## Setup

gfloat declares `requires_python >= 3.8.1` but uses `match` statements and
**actually needs 3.10+**. It imports and then fails with a `SyntaxError` in
`round.py`. The default conda env on this machine is 3.8, so use `python3.12`:

```bash
python3.12 -m venv ~/venvs/gfloat
~/venvs/gfloat/bin/pip install -r generators/saturn/benchmarks/common-data-gen/requirements.txt
```

## Trusting the reference

Before relying on gfloat, confirm it agrees with Spike on the formats Spike does
support. The committed `vec-mx-unary/data.S` was generated by Spike with
`--isa=..._zvfofp8min`, so it is an independent golden model:

```bash
cd generators/saturn/benchmarks/vec-mx-unary/gen_data
~/venvs/gfloat/bin/python validate_gfloat.py
```

Current status — all six FP8 arrays, 128/128 each:

```
  e4m3_narrow            128/128  ok
  e5m2_narrow            128/128  ok
  e4m3_narrow_sat        128/128  ok
  e5m2_narrow_sat        128/128  ok
  e4m3_widen             128/128  ok
  e5m2_widen             128/128  ok
  PASS: gfloat agrees with Spike on every OCP FP8 conversion.
```

This needs no RISC-V toolchain and no simulator, so it works as a plain CI
check. Re-run it after any gfloat upgrade.

One thing it established empirically: the RVV `.sat` instruction variant clamps
**infinities** as well as finite out-of-range values. Under the naming in P3109
v4.0.3 that is `SatFinite`; the plain variant is `SatNone`, which is also the
projection the standard's conformance floor requires (§4.5, with
ρ = (NearestTiesToEven, SatNone)). The mode the hardware lacks is
`SatPropagate` — preserve infinities, clamp finite out-of-range.

Beware that report v2.0 used the word `SatFinite` for a **different** mode. The
three modes were renamed *and* reassigned between v2.0 and v4.0.3, so always
cite the version.

## Regenerating data.S

```bash
cd generators/saturn/benchmarks/vec-mx-unary/gen_data
~/venvs/gfloat/bin/python gen_data.py --std ocp   > ../data.S   # current RTL
~/venvs/gfloat/bin/python gen_data.py --std p3109 > ../data.S   # P3109 build
```

Spec baseline: Interim Report v4.0.3 (1 Sept 2026). gfloat 0.5.2 predates it;
see the mode-mapping table at the top of `gfloat_ref.py`.

The `--std` flag must match how the RTL was built. Under the compile-time
format-select plan, `altfmt=0`/`altfmt=1` mean E4M3/E5M2 in an OCP build and
binary8p4/binary8p3 in a P3109 build; the instruction encodings are identical
either way. The array names (`e4m3_*`, `e5m2_*`) are kept verbatim so `main.c`
compiles unchanged — the generated file records which standard it holds in a
header comment.

The generated vectors are deliberately harder than the originals, which were
random values in a narrow range and rarely reached the interesting encodings.
Each array now leads with: `±0` (including `-0`, which P3109 must flush to
`0x00` rather than the `0x80` NaN code point), `±Inf`, NaN, values straddling
the overflow threshold, values inside the top binade (where the encoder splices
a wider-exponent rounder), the subnormal boundary, exact ties, and tiny
negatives that round to zero.

## Running the test

`make run` in `benchmarks/` uses Spike, which will disagree with a P3109 build.
Run against the RTL instead:

```bash
cd generators/saturn/benchmarks
make vec-mx-unary.riscv                       # needs riscv64-unknown-elf-gcc

cd $CHIPYARD/sims/verilator
make CONFIG=MXV256D128ShuttleConfig \
     BINARY=$CHIPYARD/generators/saturn/benchmarks/vec-mx-unary.riscv \
     run-binary
```

`MXV256D128ShuttleConfig` and `MXV256D128RocketConfig` (in
`generators/saturn/chipyard/SaturnConfigs.scala`) are the configs built with
`VectorParams.mxParams`, i.e. `useMxConversion = true`.

The test needs no toolchain extension support: `common/rvv_mx.h` emits the FP8
conversions as raw `.insn` encodings, so plain `-march=rv64gcv_zfh_zvfh` works.
That holds for P3109 too, since the encodings are unchanged.

## Scope

This is the integration tier: 128 vectors per conversion, a few minutes of
Verilator, and it exercises the full path from `vsetvli` through the vector
register file to `FPConvBlock`.

It is not exhaustive, and it should not be the only tier. An exhaustive sweep
belongs in a chiseltest unit test driving `FPConvBlock` directly — all 65536
BF16 patterns take gfloat 0.11 s to produce, and every rounding and saturation
mode is reachable there without going through `vtype`. That requires adding
chiseltest to the `saturn` project in `build.sbt`, which it does not currently
have.
